# 自定义分流

目前，用户只能使用订阅自带的分流规则。本文设计一种新的用法：订阅只提供节点，分流规则和策略组由用户自己组织。
相关决策是 [roadmap.md](roadmap.md) 中的 D15（已定）、D16 和 D17（待定），实施计划见 roadmap 的 M8。

状态：概念已定，原型正在重新设计，尚未实现。

## 1. 概念

- **订阅的用途**：每份订阅或本地配置都有一个用途，导入时选择，之后也可以修改。
  - **完整配置**：节点、策略组、规则全部照用订阅里的，也就是现在的行为。
  - **节点源**：只取订阅里的 `proxies`，忽略它的策略组、规则和其他设置。
- **节点池**：所有用途为"节点源"的订阅，节点合在一起组成节点池。每个节点记录它来自哪份订阅；同名节点按来源区分，
  不会互相覆盖。某份订阅更新失败时，节点池保留它上次成功下载的节点。
- **分流方案**：一套由用户维护的策略组和规则，与订阅解耦，更换订阅不影响方案（D15）。
  - 可以建多套方案，例如"日常""游戏"，随时切换。
  - 首次使用时，按内置模板生成一套默认方案。
- **当前使用**：同一时间只用一样东西，要么是一份"完整配置"的订阅，要么是一套分流方案。分流方案使用节点池里的节点。

## 2. 策略组

- **类型**：手动选择（`select`）、自动选择（`url-test`）、故障转移（`fallback`）、负载均衡（`load-balance`）。
  后三种可以设置测速地址、间隔和容差，这几项放在"高级"里。
- **成员**：从节点池里筛选，几种条件取并集，再排除一部分。
  - **地区**：按节点名称识别，如香港、台湾、日本、新加坡、美国。识别规则是内置的一组正则，界面上显示每个地区的节点数。
  - **来源订阅**：选择一份或多份节点源。
  - **关键字**：按名称包含的关键字或正则筛选。
  - **手动挑选**：直接勾选具体节点。
  - **排除**：按关键字或正则排除，例如排除名称里带"过期""剩余流量"的节点。
  - 还可以加入其他策略组，以及 `DIRECT`、`REJECT`。
- **预览**：编辑时实时列出当前匹配到的节点。节点池变化后，成员按条件重新计算，不需要手动维护。

## 3. 规则

- **第一版支持的类型**（D15）：
  - GEOSITE 分类，如 `cn`、`openai`、`category-ads-all`；
  - GEOIP 分类，如 `cn`、`private`；
  - 域名后缀、域名关键字、完整域名；
  - IP-CIDR（IPv4、IPv6），可以设置 `no-resolve`。

  进程名规则和远程规则集（rule-providers）不在第一版内。
- **目标**：某个策略组、直连（`DIRECT`）或拒绝（`REJECT`）。
- **顺序**：从上到下依次匹配，可以拖动调整顺序；每条规则可以单独停用。
- **兜底**：列表末尾固定一条"其他流量"（`MATCH`），用户只能修改它的目标。
- **分类选择**：GEOSITE、GEOIP 的分类用可搜索的列表选择，数据来自 MetaCubeX 的 meta-rules-dat。分类列表从哪里获取
  属于待决策的 D17。
- **批量添加**：域名、IP 段可以一次粘贴多行，每行一条。

## 4. 默认模板

首次使用时，生成一套名为"默认"的方案。内容可以随时修改，模板本身随版本更新，但不会覆盖已有方案。

| 策略组 | 类型 | 成员 |
| --- | --- | --- |
| 节点选择 | 手动选择 | 自动选择、各地区组、全部节点 |
| 自动选择 | 自动选择 | 全部节点 |
| 各地区组（香港、日本、美国……） | 自动选择 | 按地区筛选，没有节点的地区不生成 |
| AI 服务 | 手动选择 | 节点选择、各地区组 |

| 规则（按顺序） | 目标 |
| --- | --- |
| `GEOSITE category-ads-all` | 拒绝 |
| `GEOSITE private`、`GEOIP private` | 直连 |
| `GEOSITE openai`、`GEOSITE anthropic` 等 AI 服务 | AI 服务 |
| `GEOSITE cn`、`GEOIP cn` | 直连 |
| 其他流量 | 节点选择 |

## 5. 生成配置

使用分流方案时，最终交给内核的配置由三部分组成：节点池、方案，再加上一份固定的基础段（DNS、嗅探等）。
之后照常进入配置准入流水线：先应用覆写，再打平台补丁，最后强制安全项（architecture.md §3.2）。

待决策的 D16 是：这份配置由谁来拼装。

- **内核侧拼装（倾向）**：界面把各节点源的 YAML 原文和方案（JSON）一起交给宿主，engine 解析节点、拼装配置。
  - 优点：YAML 只在 Go 里解析；界面不需要新增 YAML 依赖；`Validate` 能直接校验拼装后的结果。
  - 代价：协议要新增"按方案启动"的请求形式。另外，界面要预览节点池和匹配到的节点，所以还需要一个解析订阅、
    返回节点列表的内核方法。
- **界面侧拼装**：界面引入 YAML 解析库，自己拼出完整配置，协议不需要改。代价是 YAML 在两种语言里各解析一次，
  而且要新增运行时依赖。

## 6. 存储与备份

- 方案、策略组、规则都存进 SQLite（[storage.md](storage.md)），每条记录有 UUID 和 `updated_at`。
- 订阅的用途和方案都会进入备份快照。换设备恢复后，节点池和方案原样还原。
- 覆写仍然有效：分流方案生成的配置同样会应用全局覆写，给高级用户留出调整空间。
