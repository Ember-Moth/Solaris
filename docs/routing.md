# 自定义分流

目前用户只能照搬订阅里的分流规则。本文设计另一种用法：订阅只提供节点，分流规则由用户自己维护，而且在新手和
高阶用户之间做到能力逐层展开，而不是把 mihomo 的配置结构原样摆上界面。

状态：已定稿（第二版，2026-10-29），尚未实现。决策是 [roadmap.md](roadmap.md) 的 D15（修订）、D16、D17，实施计划是
M8a 和 M8b。第一版里"每份订阅一个用途"的设计已取消，原因见第 11 节。

## 1. 设计原则

1. **默认路径零新概念**：导入订阅就能连接，行为和其他客户端一致。想改分流的人，第一步是"让某个服务走某个地区"，
   不需要先理解策略组。
2. **能力逐层展开**：常用的放在表面，进阶的收在"更多条件""其他类型"里，最底层的 YAML 用覆写和"查看生成的配置"兜底。
3. **一个状态只有一个地方选**："当前用哪套规则"只在分流页选；其他页面只显示，或者提供跳转到同一操作的快捷方式。
4. **以内核语义为准**：节点筛选、规则匹配都由内核（mihomo）计算，界面上的预览和测试调用同一套逻辑，不在 Python 里
   重新实现一遍。
5. **改动立即可见，也可撤销**：每次确认的改动立即生效；删除可以撤销；生效前先校验，无效的改动保存不了。

## 2. 概念

| 概念 | 含义 | 谁会接触到 |
| --- | --- | --- |
| 分流方式 | 全局开关："订阅自带"或"我的方案" | 所有人（只是一个开关） |
| 节点池 | "我的方案"下，所有订阅的节点合在一起，去掉信息节点后的集合 | 所有使用"我的方案"的人 |
| 分流方案 | 一组规则加一组策略组。可以有多套，同时只用一套 | 想要多套规则的人 |
| 规则条目 | 列表里的一行，表示一个意图，如"Telegram → 美国"；在内核里可以展开成多条规则 | 所有使用"我的方案"的人 |
| 策略组 | 内置的"节点选择""自动选择"、自动生成的地区组，以及用户自建的组 | 只有高阶用户需要编辑 |
| 其他流量 | 规则列表末尾固定的兜底一行 | 所有使用"我的方案"的人 |

"模式（规则 / 全局 / 直连）"是 mihomo 原有的概念，仍然在概览页。新开关因此叫"分流方式"，避免和它混淆。

## 3. 使用路径

### 3.1 新手：导入就用

1. 导入一份订阅。导入时不问用途。
2. 第一次导入时自动选择分流方式（5.1 节）：订阅带规则就用"订阅自带"，只有节点就用"我的方案"的默认模板。
3. 连接。概览页"当前使用"一行写明在用什么，例如"「示例订阅 A」自带的规则"，旁边给一个链接"改用我的方案"。

### 3.2 进阶：调整几个服务

1. 分流页切到"我的方案"。第一次切换时，按默认模板生成一套方案（第 6 节）。
2. 点"添加规则"，选"Telegram"，目标选"日本"，确定后立即生效。
3. 有疑问时，在规则列表上方的测试框里输入 `web.telegram.org`，看命中哪条规则、最终走哪个节点。

### 3.3 高阶：自己组织

- 在"策略组"标签里新建组，按地区、来源订阅、关键字或正则筛选成员，或手动挑选，再按条件排除。
- 用"其他类型"添加 GEOSITE / GEOIP 分类、域名、IP 段。
- 从订阅的规则"以此创建方案"，或导入一份 mihomo 配置作为起点；把方案导出成 YAML 分享。
- 在"查看生成的配置"里核对最终交给内核的内容；更底层的需求用全局覆写。

## 4. 界面

### 4.1 侧栏

概览 / 代理 / 订阅 / 分流 / 连接 / 日志 / 设置。"配置"改名"订阅"，英文 "Subscriptions"。

### 4.2 订阅页：只管来源

- 一个列表，不再分组。每行显示名称、来源（订阅链接或本地文件）、节点数、用量、到期时间、更新时间。
- 状态写在行内第二行的 `caption` 里，不用徽章：
  - "规则使用中"：分流方式是"订阅自带"，且用的正是这份订阅；
  - "不加入节点池"：分流方式是"我的方案"，且这份订阅被排除在节点池之外。
- "更多"菜单：更新、复制订阅链接、编辑覆写…、使用它的规则、不加入节点池 / 加入节点池、删除。
  其中"使用它的规则"是快捷方式，等同于在分流页切到"订阅自带"并选中这份订阅。
- 导入表单只有链接（或文件）和名称两项，没有"用途"。

### 4.3 分流页

标题栏左边是"分流"和一行状态文字，右边是分段控件"订阅自带 / 我的方案"。

**订阅自带**

- 第一行是下拉框"使用的订阅"，右侧是按钮"以此创建我的方案"（4.7 节）。按钮放在顶部，是因为订阅的规则常有几百条，
  放在底部要滚到最后才看得到。
- 下面只读展示这份订阅的策略组和规则：规则逐条列出，带搜索。
- 下拉框里，只有节点的订阅不可选，并注明"只有节点"。所有订阅都只有节点时，提示"订阅里没有规则"，并给出"改用我的方案"。

**我的方案**

- 标题栏下方一行：
  - 方案下拉框，菜单依次是各方案、分隔线、新建…、复制…、重命名…、导入…、导出…、分隔线、删除；
  - 右侧是"添加规则"按钮，以及一个"更多"菜单：查看生成的配置…、节点池设置…（两个对话框在 M8b 设计）。
- 两个标签："规则"（默认）和"策略组"。
- 规则标签：
  - 顶部是测试框"输入域名或 IP 测试"，旁边是搜索和按目标筛选；
  - 规则列表每行：拖动手柄、启用复选框、名称（如 "Telegram"、"自定义域名（12 个）"、"GEOSITE · cn"）、
    一行 `caption` 说明匹配内容、目标、"更多"菜单（编辑…、上移、下移、删除）；
  - 目标暂时不可用时（例如"美国"地区当前没有节点），目标后面写 `warning` 色的"无节点，暂走节点选择"；
  - 末尾固定"其他流量"一行，只能改目标；
  - 测试命中的那一行高亮，并在测试框下方写出"命中「Telegram」 → 日本 → 东京 03"。
- 策略组标签：
  - 列表分三段：内置（节点选择、自动选择）、地区（自动生成）、自建；
  - 地区组标"自动"，不能删除，但可以改类型（默认自动选择）或隐藏；
  - "新建策略组"按钮；每行"更多"菜单：编辑…、复制…、删除。
- 节点池为空时，规则标签上方提示"节点池里还没有节点"，并给出"导入订阅"。

### 4.4 添加规则对话框

- 第一行是分段控件"服务 / 分类 / 域名 / IP 段"，默认"服务"。
- **服务**：可搜索的列表，按类别分组（基础、AI、流媒体、社交通讯、游戏、开发、Apple、Microsoft、Google），
  可以多选；已经在方案里的服务不可选，并注明"已添加"。"基础"类别里是私有网络、国内常用和广告。
- **分类**：GEOSITE / GEOIP 二选一，再从可搜索的分类列表里选，可以多选；列表来自内核（8.4 节）。
- **域名**：多行文本框，每行一个，前缀表示类型：直接写域名表示"后缀匹配"，`=` 开头表示完整匹配，
  `~` 开头表示关键字。编辑框下方实时显示"识别出 12 个，其中 1 行无效"，并标出无效的行；有无效行时"添加"按钮
  不可用，改正或删掉这些行后才能添加。
- **IP 段**：多行文本框，每行一个 CIDR，IPv4 / IPv6 都可以；"不解析域名（no-resolve）"默认勾选。
- **目标**：下拉框，依次是节点选择、自动选择、分隔线、各地区、分隔线、自建策略组、分隔线、直连、拒绝。
  选服务时，目标默认取服务清单里的建议值（第 7 节）。
- **位置**：新规则插在列表最前面（例外规则优先），之后可以拖动。
- 多选服务或分类时，每个服务、每个分类各生成一条规则条目；域名和 IP 段一次粘贴生成一条条目。

### 4.5 策略组编辑器

- 宽 840px，左边条件，右边实时预览匹配到的节点（名称、来源订阅、延迟）。
- 默认只显示：名称、类型（手动选择 / 自动选择 / 故障转移 / 负载均衡）、地区（复选框，带节点数）。
- "更多条件"展开后：来源订阅、名称包含（关键字或正则）、手动挑选、其他成员（其他策略组、直连、拒绝）、排除。
- "高级"展开后：测速地址、间隔、容差；负载均衡的策略。
- 成员的计算规则：地区、来源订阅、名称包含三者取并集，再减去排除；手动挑选的节点和其他成员总是加入，不受排除影响。
  对话框里在"排除"下方写明这一点。

### 4.6 概览、代理与连接

- 概览页"出站"分组加一行"当前使用"："「日常」方案"或"「示例订阅 A」自带的规则"，点击跳到分流页。
- 代理页：使用"我的方案"时，节点表多一列"来源"；地区组折叠在一个"地区"小节里。
- 连接页：规则一列第一行显示规则条目的名称（如 "Telegram"），第二行用 `caption` 写内核的原始规则。

### 4.7 从订阅创建方案、导入与导出

- "以此创建我的方案"和"导入…"走同一个转换：
  - 策略组原样转成自建策略组；与内置组同名的（如"节点选择""自动选择"）并入内置组，不另建同名组；
  - GEOSITE、GEOIP、DOMAIN、DOMAIN-SUFFIX、DOMAIN-KEYWORD、IP-CIDR、IP-CIDR6 转成对应的规则条目；
  - 其他规则（进程、规则集、逻辑规则等）保留为"原始规则"条目：只读，可以排序、停用、删除。
- 转换前先列出摘要，例如"28 个策略组（其中 2 个并入内置组）、412 条规则，其中 37 条保留为原始规则"，确认后创建。
- 导出：生成 mihomo 兼容的 `proxy-groups` 和 `rules` 片段（YAML），可以复制或另存为文件。

## 5. 行为细节

### 5.1 分流方式的默认值

- 第一次导入订阅时（此前从未选过分流方式），由内核检查订阅：有 `rules` 就选"订阅自带"并使用这份订阅；
  只有节点（包括 base64 分享链接格式）就选"我的方案"并按模板生成默认方案。
- 之后再导入不改变分流方式。
- 当前使用的订阅被删除时：还有其他带规则的订阅，就改用最早导入的那一份，并给出提示；一份都没有，就切到"我的方案"。

### 5.2 节点池

- 分流方式为"我的方案"时，所有订阅都在节点池里，除非这份订阅被设成"不加入节点池"。
- **信息节点**：默认排除名称匹配 `剩余|到期|过期|流量|官网|套餐|expire|traffic|website` 的节点。这条表达式可以在
  分流页"更多"菜单的"节点池设置…"里修改。
- **重名**：两份订阅里有同名节点时，后导入的那一份的重名节点名后面加" · 订阅名"。
- **订阅失效**：下载失败时沿用上次成功下载的节点，订阅页在这份订阅的行内显示 `warning` 色的失败原因。

### 5.3 地区识别与地区组

- 内置一张地区表：每个地区有中英文名称、旗帜 emoji、常见写法和代码的正则，例如
  `🇭🇰|香港|港|HK|Hong ?Kong`。认不出地区的节点归入"其他地区"。
- 每个有节点的地区生成一个地区组，默认类型是"自动选择"。节点池变化后自动增删地区组。
- 规则的目标是某个地区，而这个地区暂时没有节点时，拼装配置时这条规则改走"节点选择"，并在规则行上提示（4.3 节）。
  这条规则本身不改，地区重新有节点后自动恢复。

### 5.4 生效、校验与撤销

- 对话框点"确定"、删除、停用、改目标，都会先校验再生效：界面把改动后的方案交给宿主 `validate`，通过后才保存，
  失败时在对话框里显示内核的原始错误，不保存。
- 正在使用的方案改动后，立即调用 `reload`。拖动排序这类连续操作，停止约 1 秒后合并成一次。
- `reload` 不断开已有连接（A2 已实测，见第 12 节）：新连接按新规则走，已有连接维持原来的路线直到结束。如果想让
  改动对已有连接也生效，到连接页点"全部关闭"。是否需要一个"规则变更后断开已有连接"的设置，留到 M8 按使用反馈
  再定；内核不会替用户断开，所以"立即生效"不会打断正在进行的下载或通话。
- 删除规则条目或策略组后，标题栏的状态文字位置显示"已删除「Telegram」· 撤销"，持续 8 秒，或者直到下一次改动。

### 5.5 删除与引用

- 删除仍被规则或其他策略组引用的策略组时，弹确认框，列出所有引用位置。确认后，引用它的规则改走"节点选择"，
  其他策略组移除它。
- 地区组和内置组不能删除。最后一套方案不能删除。

### 5.6 覆写

- 全局覆写对两种分流方式都生效。
- 订阅自己的覆写只在"订阅自带"方式下、并且用的是这份订阅时生效；在"我的方案"下，订阅只贡献节点，它的覆写不参与。
- 拼装顺序：节点池、方案和基础段 → 全局覆写 → 平台补丁 → 安全项（architecture.md §3.2）。

## 6. 默认模板

**策略组**

| 策略组 | 类型 | 成员 |
| --- | --- | --- |
| 节点选择 | 手动选择 | 自动选择、各地区组、直连 |
| 自动选择 | 自动选择 | 节点池里的全部节点 |
| 地区组（香港、日本、美国……） | 自动选择 | 按地区自动生成 |

**规则（从上到下）**

| 规则条目 | 目标 |
| --- | --- |
| 广告 | 拒绝 |
| 私有网络（`GEOSITE private`、`GEOIP private`） | 直连 |
| OpenAI | 美国；没有美国节点时为节点选择 |
| Anthropic | 美国；没有美国节点时为节点选择 |
| Gemini | 美国；没有美国节点时为节点选择 |
| 国内常用（`GEOSITE cn`、`GEOIP cn`） | 直连 |

表中每一行都是服务清单里的一个服务，所以在添加规则对话框里会显示"已添加"。
| 其他流量 | 节点选择 |

**基础段**：DNS（fake-ip，国内域名走国内 DoH，代理服务器的域名单独解析）、域名嗅探、GEO 数据的下载地址和更新周期。
基础段由我们维护，随版本更新，不在界面上编辑；需要调整的用户用全局覆写。

## 7. 服务清单

- 随应用发布的一份 JSON 文件，每个服务包含：
  - `id`、中英文名称、类别；
  - 匹配项列表，例如 `GEOSITE telegram` 加上 `GEOIP telegram`（带 `no-resolve`）；
  - 建议的目标，例如"美国"或"节点选择"。
- 第一版收录约 40 个常用服务。每个服务只对应一个具体的服务或用途，不设"AI 服务"这类合集，避免和单项重复。
- CI 检查清单里引用的分类在 MetaCubeX meta-rules-dat 里确实存在。
- 清单随应用版本更新。已经加到方案里的服务条目保存的是服务 `id`，拼装时按当前清单展开，所以清单更新后自动生效。

## 8. 内核与协议

### 8.1 D16：配置在内核里拼装

- 理由：YAML 只在 Go 里解析；节点筛选用 mihomo 自己的正则实现（regexp2，与 Python 的 `re` 不同），预览和实际
  结果一致；`validate` 校验的就是最终配置。
- `ValidateRequest`、`StartRequest`、`ReloadRequest` 的配置来源改成二选一：
  - 订阅原文 `config_yaml`（订阅自带）；
  - `Composition`：各订阅的 `{id, 名称, YAML 原文}`、节点池设置（排除的订阅、信息节点表达式）、方案（JSON）。
- 拼装方式：每份订阅转成一个内联的 proxy-provider，重名用 provider 的后缀覆写处理；地区组和条件筛选生成
  `include-all` / `use` 加 `filter`、`exclude-filter` 的策略组；规则条目按顺序展开成 mihomo 规则。
  具体字段在实现时按钉住的 mihomo 版本核实。
- 拼装结果附带一张对照表：生成的第 N 条规则来自哪个规则条目。规则测试和连接页的规则名称都用它。

### 8.2 新增方法

| 方法 | 作用 |
| --- | --- |
| `InspectSource` | 解析一份订阅：节点列表（名称、类型、识别出的地区）、有没有规则、策略组和规则的数量 |
| `PreviewGroup` | 按方案草稿和节点池计算一个策略组的成员，供编辑器实时预览 |
| `MatchRule` | 用当前配置或方案草稿匹配一个域名或 IP（可带端口、协议），返回命中的规则条目、策略组和最终节点 |
| `ListGeoCategories` | GEOSITE / GEOIP 分类名列表和数据版本 |
| `ConvertToPlan` | 把一份订阅或 mihomo 配置转成方案（4.7 节） |
| `ExportPlan` | 把方案生成为 YAML 片段 |

这些方法在 Windows 服务和 macOS 扩展里都提供；只读，不改变运行状态。

### 8.3 规则测试

- `MatchRule` 用 mihomo 的规则匹配逻辑。遇到 IP 类规则且输入是域名时，按配置的 DNS 解析一次。
- 对草稿测试时，内核临时构建规则，不应用到运行中的实例。

### 8.4 D17：GEO 数据与分类列表

- 分类列表由内核从它正在使用的 geosite / geoip 数据里读出，和实际匹配用的是同一份数据。
- 安装包附带一份初始的 GEO 数据（MetaCubeX meta-rules-dat），第一次启动不必等下载；之后由内核按基础段里的周期更新。
- 应用另外附带一份分类名清单作兜底，用于内核还没有 GEO 数据时的选择器。

## 9. 数据与存储

- 存进 M7 的 SQLite（[storage.md](storage.md)），并进入备份快照。
- 表（草案）：
  - `routing_state`：分流方式、"订阅自带"时用的订阅、"我的方案"时用的方案、节点池设置；
  - `plans`：`id`、名称、兜底目标、位置、时间戳、软删除；
  - `plan_groups`：`id`、方案、种类（内置 / 地区 / 自建）、类型、条件（JSON）、高级参数（JSON）、是否隐藏、位置；
  - `plan_rules`：`id`、方案、位置、是否启用、种类（服务 / 分类 / 域名 / IP 段 / 原始）、内容（JSON）、目标；
  - `profiles` 增加 `in_pool`（是否加入节点池），去掉第一版设计里的 `usage`。
- 目标存的是策略组 `id` 或 `DIRECT`、`REJECT`；地区组的 `id` 由地区代码派生，节点池变化后保持不变。

## 11. 对第一版设计的调整

| 第一版 | 本版 | 原因 |
| --- | --- | --- |
| 每份订阅有用途（完整配置 / 节点源），导入时选择 | 一个全局的分流方式；订阅只有"是否加入节点池" | 导入时的用途问题新手答不上来；"当前使用"分散在两个页面 |
| 方案列表占分流页左栏 | 方案是标题栏下方的下拉框 | 多数人只有一套方案 |
| 规则与内核规则一一对应 | 一个规则条目表示一个意图，可以展开成多条 | 列表短，读起来像"谁走哪里"；需要核对时看生成的配置 |
| 策略组编辑器默认展开全部条件 | 默认只有地区，其余收进"更多条件" | 新手只需要地区 |
| 编辑正在使用的方案后点"应用" | 每次确认的改动立即生效，连续操作合并 | 忘记点"应用"比多一次重载代价更大 |
| 手动挑选的节点也受排除影响 | 手动挑选和其他成员不受排除影响 | 手动挑选是明确的意图 |

## 12. 待验证

- ~~mihomo 在只改规则和策略组、不改节点时，重载会不会断开已有连接~~。A2 实测（mihomo v1.19.33，开发服务，
  2026-10-29）：不会，5.4 节的"立即生效"成立。经混合端口建立一条持续下载的连接，分别只改规则（覆写
  `prepend-rules`）、删掉一个节点并改策略组（订阅更新）、切换到另一份配置、切换模式、改混合端口，连接都完整收完，
  没有中断；重载后的新请求按新配置走。原因在 `hub/executor.ApplyConfig`：`updateProxies` / `updateRules`
  只是替换 `tunnel` 里的代理表和规则表，已建立的连接由 `statistic.DefaultManager` 持有，引用的是建立时的出站
  对象，重载不去关闭它们；入站监听器（`listener.ReCreateMixed` 等）只在地址变化时重建，关闭的也只是监听
  socket。代价是应用期间（毫秒级）隧道处于 Suspend，这一瞬间新到的连接会被关闭（`tunnel.isHandle`）。端到端
  测试 `tests/e2e` 的 `test_reloads_keep_connections` 持续覆盖这一点，升级 mihomo 时会发现行为变化。
