# 自定义分流

订阅可以带着自己的分流规则，也可以只提供节点。本文设计后一种用法：分流规则由用户自己维护，而且在新手和高阶
用户之间做到能力逐层展开，而不是把 mihomo 的配置结构原样摆上界面。

状态：已实现（M8a、M8b）。第 8 节按内核的实现写成，界面见 [ui.md](ui.md) 第 9 节，与本文不同的地方写在各节的
"实现"注里。决策是 [roadmap.md](roadmap.md) 的 D15、D16、D17。

## 1. 设计原则

1. **默认路径零新概念**：导入订阅就能连接，行为和其他客户端一致。想改分流的人，第一步是"让某个服务走某个地区"，
   不需要先理解策略组。
2. **能力逐层展开**：常用的放在表面，进阶的收在"更多条件""其他类型"里，最底层的 YAML 用覆写和"查看生成的配置"兜底。
3. **一个状态只有一个地方选**："当前用哪套规则"只在分流页选；其他页面只显示，或者提供跳转到同一操作的快捷方式。
4. **以内核语义为准**：节点筛选、规则匹配都由内核（mihomo）计算，界面上的预览和测试调用同一套逻辑，不在 Python 里
   重新实现一遍。
5. **改动立即可见，也可撤销**：每次确认的改动立即生效；删除可以撤销；生效前先校验，无效的改动保存不了。

## 2. 概念

| 概念 | 含义 | 谁会接触到 |
| --- | --- | --- |
| 分流方式 | 全局开关："订阅自带"或"我的方案" | 所有人（只是一个开关） |
| 节点池 | "我的方案"下，所有订阅的节点合在一起，去掉信息节点后的集合 | 所有使用"我的方案"的人 |
| 分流方案 | 一组规则加一组策略组。可以有多套，同时只用一套 | 想要多套规则的人 |
| 规则条目 | 列表里的一行，表示一个意图，如"Telegram → 美国"；在内核里可以展开成多条规则 | 所有使用"我的方案"的人 |
| 策略组 | 内置的"节点选择""自动选择"、自动生成的地区组，以及用户自建的组 | 只有高阶用户需要编辑 |
| 其他流量 | 规则列表末尾固定的兜底一行 | 所有使用"我的方案"的人 |

"模式（规则 / 全局 / 直连）"是 mihomo 原有的概念，仍然在概览页。新开关因此叫"分流方式"，避免和它混淆。

## 3. 使用路径

### 3.1 新手：导入就用

1. 导入一份订阅。导入时不问用途。
2. 第一次导入时自动选择分流方式（5.1 节）：订阅带规则就用"订阅自带"，只有节点就用"我的方案"的默认模板。
3. 连接。概览页"当前使用"一行写明在用什么，例如"「示例订阅 A」自带的规则"，旁边给一个链接"改用我的方案"。

### 3.2 进阶：调整几个服务

1. 分流页切到"我的方案"。第一次切换时，按默认模板生成一套方案（第 6 节）。
2. 点"添加规则"，选"Telegram"，目标选"日本"，确定后立即生效。
3. 有疑问时，在规则列表上方的测试框里输入 `web.telegram.org`，看命中哪条规则、最终走哪个节点。

### 3.3 高阶：自己组织

- 在"策略组"标签里新建组，按地区、来源订阅、关键字或正则筛选成员，或手动挑选，再按条件排除。
- 用"其他类型"添加 GEOSITE / GEOIP 分类、域名、IP 段。
- 从订阅的规则"以此创建方案"，或导入一份 mihomo 配置作为起点；把方案导出成 YAML 分享。
- 在"查看生成的配置"里核对最终交给内核的内容；更底层的需求用全局覆写。

## 4. 界面

### 4.1 侧栏

概览 / 代理 / 订阅（Subscriptions）/ 分流 / 连接 / 日志 / 设置。

### 4.2 订阅页：只管来源

- 一个列表，不分组。每行显示名称、来源（订阅链接或本地文件）、节点数、用量、到期时间、更新时间。
- 状态写在行内第二行的 `caption` 里，不用徽章：
  - "规则使用中"：分流方式是"订阅自带"，且用的正是这份订阅；
  - "不加入节点池"：分流方式是"我的方案"，且这份订阅被排除在节点池之外。
- "更多"菜单：更新、复制订阅链接、编辑覆写…、使用它的规则、不加入节点池 / 加入节点池、删除。
  其中"使用它的规则"是快捷方式，等同于在分流页切到"订阅自带"并选中这份订阅。
  实现：菜单在"更新"之后有"每 12 小时自动更新"勾选项；只有节点的订阅的"使用它的规则"不可用。
- 导入表单只有链接（或文件）和名称两项。

### 4.3 分流页

标题栏左边是"分流"和一行状态文字，右边是分段控件"订阅自带 / 我的方案"。

**订阅自带**

- 第一行是下拉框"使用的订阅"，右侧是按钮"以此创建我的方案"（4.7 节）。按钮放在顶部，是因为订阅的规则常有几百条，
  放在底部要滚到最后才看得到。
- 下面只读展示这份订阅的策略组和规则：规则逐条列出，带搜索。
- 下拉框里，只有节点的订阅不可选，并注明"只有节点"。所有订阅都只有节点时，提示"订阅里没有规则"，并给出"改用我的方案"。

**我的方案**

- 标题栏下方一行：
  - 方案下拉框，菜单依次是各方案、分隔线、新建…（从默认模板或复制一个方案）、复制…、重命名…、导入…、导出…、
    分隔线、删除；
  - 右侧是"添加规则"按钮，以及一个"更多"菜单：查看生成的配置…、节点池设置…。
- 两个标签："规则"（默认）和"策略组"。
- 规则标签：
  - 顶部是测试框"输入域名或 IP 测试"，旁边是搜索和按目标筛选；
  - 规则列表每行：拖动手柄、启用复选框、名称（如 "Telegram"、"自定义域名（12 个）"、"GEOSITE · cn"）、
    一行 `caption` 说明匹配内容、目标、"更多"菜单（编辑…、上移、下移、删除）；
  - 目标暂时不可用时（例如"美国"地区当前没有节点），目标后面写 `warning` 色的"无节点，暂走节点选择"；
  - 末尾固定"其他流量"一行，只能改目标；
  - 测试命中的那一行高亮，并在测试框下方写出"命中「Telegram」 → 日本 → 东京 03"。
- 策略组标签：
  - 列表分三段：内置（节点选择、自动选择）、地区（自动生成）、自建；
  - 地区组标"自动"，不能删除，但可以改类型（默认自动选择）或隐藏；
  - "新建策略组"按钮；每行"更多"菜单：编辑…、复制…、删除。
  - 之后是"组网"一节（[mesh.md](mesh.md) 第 5 节）和"链式出口"一节：WARP、Tor、VPN Gate 出口（[exits.md](exits.md)
    第 6 节）。
- 节点池为空时，规则标签上方提示"节点池里还没有节点"，并给出"导入订阅"。

实现：
- 标题栏下方的主按钮随标签变：规则标签是"添加规则"，策略组标签是"新建策略组"。
- 测试框边输入边测（停顿 0.4 秒后，回车立即测），可以写 `域名:端口`、`[IPv6]:端口`，也可以粘贴链接；不是域名或
  IP 时在下方写"「…」不是域名或 IP"。结果写在测试框下方，例如"命中「Telegram」 → 🇯🇵 日本 → 东京 03"：
  条目名称由界面给出，链路是内核里的组名和节点名（直连、拒绝按界面语言写）；命中覆写插入的规则时写
  "命中覆写的规则 DOMAIN,x → …"，用到了 DNS 时末尾写"（解析为 1.2.3.4）"。测的是界面上显示的方案；方案改动
  生效后自动重测。命中的行（包括"其他流量"）用 `surface-selected` 底色标出。
- 搜索匹配条目名称、说明和目标，不区分大小写；按目标筛选的下拉框列出"全部目标"和规则用到的目标，顺序同目标
  下拉框。筛选时拖动手柄降到 40% 不透明度且不能拖动，"上移""下移"仍按完整列表移动；没有匹配时写"没有匹配
  的规则"。
- 策略组标签分内置、地区、自建三段。自建组的名称是按钮，点击编辑；"更多"菜单是编辑…、复制…、删除。内置组和
  地区组的菜单在类型和显示 / 隐藏之后加"复制为自建策略组…"，从它的成员条件开始一个新组（地区组是这个地区）。
- 链式出口一节只有 WARP 出口；目标下拉框里也只有它（Tor、VPN Gate 未实现）。

### 4.4 添加规则对话框

- 第一行是分段控件"服务 / 分类 / 域名 / IP 段"，默认"服务"。
- **服务**：可搜索的列表，按类别分组（基础、AI、流媒体、社交通讯、游戏、开发、Apple、Microsoft、Google），
  可以多选；已经在方案里的服务不可选，并注明"已添加"。"基础"类别里是私有网络、国内常用和广告。
- **分类**：GEOSITE / GEOIP 二选一，再从可搜索的分类列表里选，可以多选；列表来自内核（8.4 节）。
- **域名**：多行文本框，每行一个，前缀表示类型：直接写域名表示"后缀匹配"，`=` 开头表示完整匹配，
  `~` 开头表示关键字。编辑框下方实时显示"识别出 12 个，其中 1 行无效"，并标出无效的行；有无效行时"添加"按钮
  不可用，改正或删掉这些行后才能添加。
- **IP 段**：多行文本框，每行一个 CIDR，IPv4 / IPv6 都可以；"不解析域名（no-resolve）"默认勾选。
- **目标**：下拉框，依次是节点选择、自动选择、分隔线、各地区、分隔线、自建策略组、分隔线、各组网出站（mesh.md）、
  分隔线、WARP 出口、Tor 出口、VPN Gate 出口（exits.md，M9、M10、M12；未启用时不可选）、分隔线、直连、拒绝。
  选服务时，目标默认取服务清单里的建议值（第 7 节）。
- **位置**：新规则插在列表最前面（例外规则优先），之后可以拖动。
- 多选服务或分类时，每个服务、每个分类各生成一条规则条目；域名和 IP 段一次粘贴生成一条条目。

### 4.5 策略组编辑器

- 宽 840px，左边条件，右边实时预览匹配到的节点（名称、来源订阅、延迟）。
- 默认只显示：名称、类型（手动选择 / 自动选择 / 故障转移 / 负载均衡）、地区（复选框，带节点数）。
- "更多条件"展开后：来源订阅、名称包含（关键字或正则）、手动挑选、其他成员（其他策略组、直连、拒绝）、排除。
- "高级"展开后：测速地址、间隔、容差；负载均衡的策略。
- 成员的计算规则：地区、来源订阅、名称包含三者取并集，再减去排除；手动挑选的节点和其他成员总是加入，不受排除影响。
  对话框里在"排除"下方写明这一点。

实现（`GroupEditor`）：
- 名称和类型在一行，下面是地区（只列有节点的地区，带节点数）；"更多条件"里依次是来源订阅（第一项"全部节点"对应
  `members.all`）、名称包含、手动挑选（"挑选"展开可搜索的节点列表）、其他成员（内置组、全部地区组、各地区组、
  其他自建组、直连、拒绝；会让组间接包含自己的项不可选）、排除。名称包含和排除各有一个"关键字 / 正则"下拉框：
  关键字是不区分大小写的子串，正则是 mihomo 的写法；界面先用 Python 检查正则，写不对时显示"正则无效"，最终以
  内核为准。
- "高级"只对自动选择、故障转移、负载均衡出现：测速地址、间隔（秒）、容差（毫秒，自动选择）、策略（负载均衡）。
  方案 JSON 里的 `timeout`、`lazy` 界面不编辑，原样保留。
- 条件改动停止 0.25 秒后调用 `PreviewGroup`；预览时组名临时用组的 id，所以名称还没填或与别的组重名时也能预览，
  名称问题在保存时由 `validate` 报出。预览先列其他成员，再列节点（名称、来源订阅、内核测得的延迟）；标题右侧写
  "6 个节点、1 个其他成员"。窗口放不下两栏时预览移到条件下方。

### 4.6 概览、代理与连接

- 概览页"出站"分组加一行"当前使用"："「日常」方案"或"「示例订阅 A」自带的规则"，点击跳到分流页。
- 代理页：使用"我的方案"时，节点表多一列"来源"；地区组折叠在一个"地区"小节里。
- 连接页：规则一列第一行显示规则条目的名称（如 "Telegram"），第二行用 `caption` 写内核的原始规则。

### 4.7 从订阅创建方案、导入与导出

- "以此创建我的方案"和"导入…"走同一个转换：
  - 策略组原样转成自建策略组；与内置组同名的（如"节点选择""自动选择"）并入内置组，不另建同名组；
  - GEOSITE、GEOIP、DOMAIN、DOMAIN-SUFFIX、DOMAIN-KEYWORD、IP-CIDR、IP-CIDR6 转成对应的规则条目；
  - 其他规则（进程、规则集、逻辑规则等）保留为"原始规则"条目：只读，可以排序、停用、删除。
- 转换前先列出摘要，例如"28 个策略组（其中 2 个并入内置组）、412 条规则，其中 37 条保留为原始规则"，确认后创建。
- 导出：生成 mihomo 兼容的 `proxy-groups` 和 `rules` 片段（YAML），可以复制或另存为文件。

实现（`PlanTransfer`；内核的转换规则见 8.8 节）：
- 摘要对话框的标题是"以「订阅名」创建方案"（导入时是文件名），正文例如"4 个策略组（其中 1 个并入内置组）、
  400 条规则，其中 80 条保留为原始规则。方案里有 216 条规则条目（相邻的同类规则合为一条）。40 条无法转换，
  不会带入方案：规则集 40 条。"规则数包括 MATCH，与订阅下拉框里的条数一致。没能转换的规则逐条列在下方（等宽字），
  然后是方案名称（默认是订阅名或文件名）和"创建后改用这套方案"（默认勾选；勾选时分流方式也切到"我的方案"）。
- "以此创建我的方案"转换的是正在使用规则的那份订阅，组里列出的节点记成这份订阅的手动挑选；"导入…"读一份 YAML
  文件，节点按名称匹配。
- 导出对话框写明"节点按订阅里的名称列出，不含节点本身"，按钮是关闭、另存为…、复制。"查看生成的配置…"用同一个
  只读对话框，只有关闭和复制。

## 5. 行为细节

### 5.1 分流方式的默认值

- 第一次导入订阅时（此前从未选过分流方式），由内核检查订阅：有 `rules` 就选"订阅自带"并使用这份订阅；
  只有节点（包括 base64 分享链接格式）就选"我的方案"并按模板生成默认方案。
- 之后再导入不改变分流方式。
- 当前使用的订阅被删除时：还有其他带规则的订阅，就改用最早导入的那一份，并给出提示；一份都没有，就切到"我的方案"。

### 5.2 节点池

- 分流方式为"我的方案"时，所有订阅都在节点池里，除非这份订阅被设成"不加入节点池"。
- **信息节点**：默认排除名称匹配 `(?i)剩余|到期|过期|流量|官网|套餐|expire|traffic|website` 的节点（不区分大小写，
  `models/routing.py` 的 `DEFAULT_INFO_PATTERN`）。这条表达式可以在
  分流页"更多"菜单的"节点池设置…"里修改。
- **重名**：两份订阅里有同名节点时，后导入的那一份的重名节点名后面加" · 订阅名"。
- **订阅失效**：下载失败时沿用上次成功下载的节点，订阅页在这份订阅的行内显示 `warning` 色的失败原因。
- **组网出站**：Tailscale、ZeroTier、EasyTier 出站不进节点池，在策略组标签的"组网"一节单独列出，作为规则目标
  （[mesh.md](mesh.md)，D24）。

### 5.3 地区识别与地区组

- 内置一张地区表：每个地区有中英文名称、旗帜 emoji、常见写法和代码的正则，例如
  `🇭🇰|香港|港|HK|Hong ?Kong`。认不出地区的节点归入"其他地区"。
- 每个有节点的地区生成一个地区组，默认类型是"自动选择"。节点池变化后自动增删地区组。
- 规则的目标是某个地区，而这个地区暂时没有节点时，拼装配置时这条规则改走"节点选择"，并在规则行上提示（4.3 节）。
  这条规则本身不改，地区重新有节点后自动恢复。

### 5.4 生效、校验与撤销

- 对话框点"确定"、删除、停用、改目标，都会先校验再生效：界面把改动后的方案交给宿主 `validate`，通过后才保存，
  失败时在对话框里显示内核的原始错误，不保存。
- 正在使用的方案改动后，立即调用 `reload`。拖动排序这类连续操作，停止约 1 秒后合并成一次。
- `reload` 不断开已有连接：mihomo 重载时只替换代理表和规则表，已建立的连接引用建立时的出站（`tests/e2e` 的
  `test_reloads_keep_connections` 守住这一点）。新连接按新规则走，已有连接维持原来的路线直到结束。如果想让改动
  对已有连接也生效，到连接页点"全部关闭"。是否需要一个"规则变更后断开已有连接"的设置，按使用反馈再定；内核不会替用户断开，所以"立即生效"不会打断正在进行的下载或通话。
- 删除规则条目或策略组后，标题栏的状态文字位置显示"已删除「Telegram」· 撤销"，持续 8 秒，或者直到下一次改动。

### 5.5 删除与引用

- 删除仍被规则或其他策略组引用的策略组时，弹确认框，列出所有引用位置。确认后，引用它的规则改走"节点选择"，
  其他策略组移除它。
- 地区组和内置组不能删除。最后一套方案不能删除。

### 5.6 覆写

- 全局覆写对两种分流方式都生效。
- 订阅自己的覆写只在"订阅自带"方式下、并且用的是这份订阅时生效；在"我的方案"下，订阅只贡献节点，它的覆写不参与。
- 拼装顺序：节点池、方案和基础段 → 全局覆写 → 平台补丁 → 安全项（architecture.md §3.2）。

## 8. 内核与协议

### 8.1 D16：配置在内核里拼装

- 理由：YAML 只在 Go 里解析；节点筛选用 mihomo 自己的正则实现（regexp2，与 Python 的 `re` 不同），预览和实际
  结果一致；`validate` 校验的就是最终配置。
- `ValidateRequest`、`StartRequest`、`ReloadRequest` 的配置来源是 oneof `source`，二选一：
  - 订阅原文 `config_yaml`（字段 1，订阅自带）；
  - `composition`（字段 4）：节点池里各订阅的 `{id, name, yaml}`，按导入顺序，不加入节点池的订阅界面不传；
    信息节点表达式 `info_filter`；方案 `plan_json`（8.5 节）。
- `overrides` 不变，在拼装之后应用。拼装结果照常进入准入流水线：拼装 → 覆写 → 平台补丁（开发模式护栏）→
  安全项（architecture.md §3.2），engine 的 `TestCompositionGoesThroughThePipeline` 守住这一顺序。订阅只贡献
  节点：它的 `rules`、端口、`tun`、控制器等字段都不进入拼装结果。
- 实现在 `src/core/internal/compose`，mihomo 的字段写法按钉住的 v1.19.33 源码核实：
  - **节点池**：每份订阅按 mihomo 的 proxy-provider 的方式读：YAML 映射取 `proxies`，否则当作分享链接（逐行或
    base64，`convert.ConvertsV2Ray`）。订阅里的 `proxy-providers` 不读。名称匹配 `info_filter` 的节点不进入
    节点池。`tailscale`、`zerotier`、`easytier` 出站也不进节点池，写在顶层 `proxies`（组网出站，mesh.md 第 3 节）。同一份订阅里同名的节点只留第一个，与 mihomo 的 provider 一样。与之前订阅的节点、mihomo 的内置名称
    （`DIRECT` 等）或任何策略组同名的节点，名称后加" · 订阅名"，仍然重名再加序号。
  - **provider**：每份有节点的订阅生成一个 `type: inline` 的 proxy-provider，名为 `pool:<订阅 id>`，payload 是
    改名后的节点。没有用 provider 的 `override.additional-suffix`：它给这个 provider 的全部节点加后缀，而 5.2 节
    只给重名的节点加。也没有用 provider 的 `exclude-filter` 排除信息节点：mihomo 对 provider 没有节点时报错
    （`file doesn't have any proxy`），由内核排除可以直接不生成这个 provider。
  - **策略组**：成员在内核里按 4.5 节计算（regexp2，与 mihomo 相同的实现和选项），再写成
    `use: [含成员的 provider]` 加只匹配这些成员名称的 `filter`（`^(?:名称1|名称2)$`，反引号写成 `\x60`，因为
    mihomo 用反引号分隔多个 filter）；成员正好是节点池全部节点时不写 `filter`。其他成员（其他策略组、直连、
    拒绝）写在 `proxies`，mihomo 把它们排在节点之前。没有用组的 `exclude-filter`：它同样作用于 `proxies` 里的
    成员（`outboundgroup.GroupBase.GetProxies`），做不到"手动挑选和其他成员不受排除影响"。没有用
    `include-all` / `include-all-providers`：它们会把覆写加进来的 provider 也算进去，和内核计算的成员不一致。
    既没有节点也没有其他成员的组写成 `proxies: [COMPATIBLE]`，与 mihomo 自己对空组的处理相同。
  - 地区识别和各种条件看的都是订阅里写的原名，不看加了后缀的名称，所以改名不会改变节点的地区和条件结果。
  - **组的顺序**：节点选择、自动选择、有节点的地区组（按地区表顺序）、自建组（按方案顺序）。代理页和
    `GLOBAL` 都按这个顺序。
  - **规则**：启用的规则条目按顺序，每个匹配项展开成一条 `类型,值,目标[,no-resolve]`；停用的条目跳过；末尾是
    `MATCH,兜底目标`。目标是没有节点的地区或没有成员的策略组时，这一条目改走"节点选择"，并在报告里给出警告；
    条目本身不改，下一次拼装时目标可用就恢复。目标是不可用的链式出口或已经不存在的组网出站时，改写为 `REJECT`
    （D21，exits.md 3.3 节、mesh.md 第 3 节）。
  - **链式出口**：有规则指向 `egress:warp` 且 `Composition.egress` 带了 WARP 账户时，生成"WARP 出口"出站，
    `dialer-proxy` 指向方案 `egress.warp.via` 的组（exits.md 3.3 节）。
- **报告** `CompositionReport`：用 composition 的 Validate、Start、Reload 返回它（用 `config_yaml` 时仍是 Empty）：
  - 警告：条目 id（兜底是 `fallback`）、原因（`region_empty` / `group_empty`，以及链式出口与组网出站的 `egress_unavailable`、
    `mesh_missing`、`via_empty`、`mesh_restricted`，见 exits.md 3.3 节、mesh.md 第 3、4 节）、方案里写的目标；
  - 生成的策略组：id、名称、种类（内置 / 地区 / 自建）、地区代码、节点数；
  - 生成的每条规则及其条目 id；
  - 节点池：新名、原名、来源订阅、类型、地区代码；
  - 组网出站：`mesh:` id、名称、类型、来源订阅。
- **规则条目对照表**：engine 为运行中的配置保存"第 N 条规则 → 条目 id"，覆写插入的规则没有条目 id。
  `ListRules` 的 `Rule.entry_id` 按位置取；连接快照的 `Connection.rule_entry_id` 按连接记录的规则类型、payload
  和链路最外层（规则的目标）查找，同一组键取第一条，与 mihomo 的匹配顺序一致。改用 `config_yaml` 时对照表清空。
- 拼装出错（方案、订阅或信息节点表达式不合法）返回 `invalid_config`，message 以 `plan: ` 或
  `subscription "名称": ` 开头；生成的配置被 mihomo 拒绝（例如 GEO 数据里没有的分类）时是 mihomo 的原文。

### 8.2 新增方法

| 方法 | 作用 | 字段号 |
| --- | --- | --- |
| `InspectSource` | 按 8.1 节的方式读一份订阅：节点（名称、类型、地区代码、是否信息节点、是否组网出站）、有没有规则、策略组和规则的数量 | 49 |
| `ListGeoCategories` | 内核 GEO 数据里的 GEOSITE / GEOIP 分类名，以及每个文件的 sha256 和修改时间 | 50 |
| `PreviewGroup` | 按方案草稿和节点池计算一个策略组的成员，供编辑器实时预览 | 51 |
| `MatchRule` | 用当前配置或方案草稿匹配一个域名或 IP（可带端口、协议），返回命中的规则条目、策略组和最终节点 | 52 |
| `ConvertToPlan` | 把一份订阅或 mihomo 配置转成方案（4.7 节） | 53 |
| `ExportPlan` | 把方案生成为 YAML 片段，或写出生成的完整配置 | 54 |

- 这些方法在 Windows 服务和 macOS 扩展里都提供；只读，不改变运行状态，也不需要内核在运行（`MatchRule` 不带配置
  来源时除外，见 8.3 节）。
- `InspectSource` 读不了订阅时返回 `invalid_config`。节点类型与 `Proxy.type` 相同（`Shadowsocks`、`Vless`……）。
- `ListGeoCategories` 在 home 里没有某个文件时，那一类的结果为空；`ServiceHost` 这时用应用附带的清单代替，
  并标为 `bundled`（8.4 节）。
- `PreviewGroup` 带 `Composition`（节点池和含这个组的方案草稿）和组 id，返回成员节点（`PoolNode`，按节点池顺序）
  和其他成员的 id（策略组 id、每个有节点的地区组 `region:XX`、`DIRECT` 等，`region:*` 已展开）。成员与拼装时
  完全相同（同一段 `resolveMembers`），所以预览就是连接后代理页显示的成员。没有节点的地区组返回空；方案不合法、
  没有这个组时是 `invalid_config`。
- `ConvertToPlan` 带 YAML、来源订阅 id（导入时为空）、`locale` 和信息节点表达式，返回方案 JSON 和摘要：策略组数、
  其中并入内置组的数目、规则数（含 MATCH）、保留为原始规则的数目、规则条目数，以及每条没能转换的规则和原因
  （`rule_set`、`sub_rule`、`target`、`after_match`、`invalid`）。规则见 8.8 节。读不了或既没有策略组也没有规则时
  是 `invalid_config`。
- `ExportPlan` 带 `Composition` 和格式：`SHARE`（默认）写可分享的片段（8.8 节）；`GENERATED` 写内核会运行的完整
  配置，覆写、`RunOptions`、平台补丁和安全项都已应用（不建 TUN 的宿主忽略 TUN 选项），节点只留 `name`、`type`、
  `server`、`port`，不显示密码、uuid 等字段。YAML 的键按常看的顺序排（`mode`、端口……`proxy-groups`、`rules`，
  组里 `name`、`type` 在前），其余按字母序。

### 8.3 规则测试

- `MatchRule` 用 mihomo 的规则匹配逻辑。遇到 IP 类规则且输入是域名时，按配置的 DNS 解析一次。
- 对草稿测试时，内核临时构建规则，不应用到运行中的实例。
- 留意：mihomo 的 hosts 表默认把 `localhost` 映射到 127.0.0.1，这样的域名在匹配规则之前就有了 IP，会命中
  `IP-CIDR` 规则（端到端测试里遇到过）。

实现：
- 请求的配置来源与 `Validate` 相同（`config_yaml` 或 `composition`，加覆写），经同一条准入流水线构建、不应用；
  不带来源时用运行中的配置，内核没在运行就是 `not_running`。界面总是带上显示的方案和全局覆写，所以内核停着也能测。
- 匹配逐条调用 mihomo 规则自己的 `Match`，循环与 `tunnel.match` 相同：第一条命中且目标存在的规则；目标经由
  `PASS` 的跳过，UDP 时跳过不支持 UDP 的目标；没有规则命中就是 `DIRECT`（`matched = false`）。不做 rematch。
- 域名先查 mihomo 当前的 hosts 表；IP 类规则需要时用内核当前的解析器解析一次（内核停着时是系统解析器），
  解析到的地址写在 `resolved_ip`。进程类规则不会命中（测试没有发起的进程）；入站类型按 TUN 是否开着记为 TUN
  或混合端口的 HTTPS。
- 链路 `chain` 与 `Connection.chains` 同序（节点在前、规则的目标在后）：内核在运行且运行的配置里有这个目标时，
  沿各组当前的选择一直走到节点；否则只有目标本身。`Rule.entry_id` 是方案的条目 id，覆写插入的规则为空。
- 宿主的读写：`ServiceHost.match_rule` 把链路反过来，目标在前，与连接页一致。

### 8.4 D17：GEO 数据与分类列表

- 内核用 `.dat` 格式（基础段 `geodata-mode: true`）匹配 GEOSITE 和 GEOIP。文件在内核的 home 里，名为
  `GeoSite.dat`、`GeoIP.dat`（mihomo 查找时不区分大小写）。`ListGeoCategories` 直接读这两个文件，只遍历
  protobuf 里的分类字段，不解码域名和 IP 段；和实际匹配用的是同一份数据。
- **附带的数据**：MetaCubeX/meta-rules-dat 的 release 分支，钉在 `be456e5`（2026-10-29 发布）。
  `geosite.dat` 4.4 MB，1563 个分类；`geoip.dat` 16.5 MB，260 个分类；共 20.9 MB。版本、大小和 sha256 写在
  `scripts/fetch_geodata.py`，与发布方的 `.sha256sum` 一致。脚本下载到 `build/geodata/`（已被 git 忽略），文件名
  已是 mihomo 的写法，打包时原样放进安装包，由内核所在的进程种进 home：打开 engine 前把 home 里缺少的文件复制
  过去（`internal/geodata` 的 `Seed`，先写临时文件再改名，不会留下半个文件），已有的不动，engine 的 GEO 更新会
  替换它们。macOS 的扩展在 attach 时复制，失败时隧道不启动；Windows 服务在打开属主的 home 时从安装目录的
  `geodata\` 复制，失败时只记一条警告，照常启动，由 mihomo 在需要时下载。开发服务（`scripts/dev.py`）启动时也会
  放一份。
- **兜底清单**：`src/solaris/host/geo_categories.py`，由 `fetch_geodata.py --categories` 从附带的数据生成，
  28 KB，带两个文件的 sha256。内核没有数据或连不上时（例如 macOS 隧道未连接），分类选择器用它。用 Python
  模块而不是数据文件，Nuitka 打包时自动带上。CI 用 `--check` 核对清单与钉住的数据一致。
- **更新**：基础段开启 `geo-auto-update`，周期 24 小时。mihomo 只在它自己的 `main` 里启动 GEO 更新器，内嵌时
  不会运行，所以 engine 在配置开启自动更新时自己运行一个：每小时检查一次，数据文件比更新周期旧时调用 mihomo 的
  `updater.UpdateGeoDatabases`，从 `geox-url` 下载（mihomo 的下载经内核自己的出站，按规则走）；内核停止时它也
  停止。新数据在下一次 Start 或 Reload 时生效，已应用的规则不变。
- 没有数据时，mihomo 在第一次需要时同步下载（解析 GEOSITE / GEOIP 规则，或基础段里的 `geosite:` DNS 策略时），
  会让那次 Validate 等上下载完成，所以安装包必须附带数据。单元测试写入一份很小的数据（`geodatatest`），
  从不下载；端到端测试用附带的数据。

### 8.5 方案 JSON（版本 1）

界面在 `plan_json` 里传方案。内核不认识的字段一律忽略，界面可以在里面放自己的字段（例如服务 id）。

```json
{
  "version": 1,
  "locale": "zh",
  "test_url": "https://www.gstatic.com/generate_204",
  "groups": [
    {"id": "proxy", "kind": "builtin", "name": "节点选择", "type": "select",
     "members": {"others": ["auto", "region:*", "DIRECT"]}},
    {"id": "auto", "kind": "builtin", "name": "自动选择", "type": "url-test",
     "members": {"all": true}, "options": {"interval": 300, "tolerance": 50}},
    {"id": "region:JP", "kind": "region", "type": "select", "hidden": false},
    {"id": "g-7f3a", "kind": "custom", "name": "低倍率", "type": "url-test",
     "members": {"regions": ["HK", "JP"], "sources": ["sub-b"],
                 "name": {"mode": "keyword", "pattern": "IPLC"},
                 "exclude": {"mode": "regex", "pattern": "[2-9]x"},
                 "nodes": [{"source": "sub-a", "name": "香港 01"}],
                 "others": ["DIRECT"]},
     "options": {"url": "https://cp.cloudflare.com", "interval": 600, "lazy": true}}
  ],
  "rules": [
    {"id": "r-ads", "kind": "service", "enabled": true,
     "items": [{"type": "GEOSITE", "value": "category-ads-all"}], "target": "REJECT"},
    {"id": "r-tg", "kind": "service",
     "items": [{"type": "GEOSITE", "value": "telegram"},
               {"type": "GEOIP", "value": "telegram", "no_resolve": true}],
     "target": "region:JP"}
  ],
  "fallback": "proxy"
}
```

| 字段 | 含义 |
| --- | --- |
| `version` | 必须是 1，否则 `invalid_config`。格式不兼容地变化时加 1 |
| `locale` | `zh`（默认）或 `en`：生成的内置组和地区组用哪种语言命名。界面另行本地化地区代码 |
| `test_url` | 没有自己 `url` 的组用它测延迟；不填用 mihomo 的默认值 |
| `groups` | 内置组、地区组的设置和自建组，见下文 |
| `rules` | 规则条目，按列表顺序展开 |
| `fallback` | 兜底目标，不填是 `proxy` |
| `egress` | 链式出口的设置，见下文和 exits.md 7.1 节 |

**策略组**

- `id`：内置组是 `proxy`（节点选择）和 `auto`（自动选择）；地区组是 `region:` 加地区代码；自建组是界面自己的 id，
  不能与前两种相同。目标、`others` 都用 id 引用策略组，地区组的 id 不随节点池变化。
- `kind`：`builtin`、`region` 或 `custom`。方案里没有写的内置组用默认设置：节点选择是手动选择，成员为
  自动选择、全部地区组、直连；自动选择是自动选择，成员为全部节点（第 6 节）。方案里写了、但地区没有节点的
  地区组不生成。
- `name`：自建组必填；内置组、地区组可填，覆盖内核按 `locale` 生成的名称（地区组是旗帜加名称，如"🇯🇵 日本"）。
  名称不能为空、不能有首尾空格、逗号或换行，不能是 mihomo 的内置名称（`DIRECT`、`REJECT`、`REJECT-DROP`、`PASS`、
  `COMPATIBLE`、`GLOBAL`），不能以 `pool:` 开头，也不能与其他组重名。
- `type`：`select`、`url-test`、`fallback`、`load-balance`。不填时内置组如上，地区组 `url-test`，自建组 `select`。
- `hidden`：从代理页隐藏（mihomo 的 `hidden`），规则仍可指向它。
- `members`（内置组和自建组；地区组的成员由地区决定，写了也忽略），按 4.5 节计算：
  - `regions`（地区代码）、`sources`（订阅 id）、`name`（名称条件）三者取并集；`all: true` 表示从全部节点开始；
  - 再减去 `exclude`（名称条件）；
  - `nodes`（手动挑选，`{source, name}`，`name` 是订阅里的原名，改名不影响）和 `others`（其他成员）总是加入，
    不受排除影响。`others` 里是策略组 id、`region:*`（全部地区组，按地区表顺序）、`DIRECT`、`REJECT`、
    `REJECT-DROP`；指向没有节点的地区时跳过。组不能把自己列为成员。
  - 名称条件是 `{"mode": "keyword" | "regex", "pattern": "…"}`：`keyword` 是不区分大小写的子串，`regex` 是
    mihomo 的正则（regexp2）。条件看订阅里的原名。
  - 不存在的订阅 id、已经不在订阅里的手动挑选节点直接忽略。
- `options`（高级参数）：`url`、`interval`（秒）、`tolerance`（毫秒，只对 `url-test`）、`timeout`（毫秒）、
  `lazy`（不填用 mihomo 的默认值 true）、`strategy`（只对 `load-balance`：`consistent-hashing`、`round-robin`、
  `sticky-sessions`）。

**规则条目**

- `id`：必填，方案内唯一，不能是 `fallback`（兜底规则的条目 id）。
- `kind`：界面的种类（`service`、`category`、`domain`、`ip`、`raw`），内核不读。服务清单归界面：界面拼方案时把
  服务展开成具体匹配项，内核只认识匹配项和条目 id。
- `enabled`：不填为 true；false 的条目不展开，也没有警告。
- `items`：至少一项，每项是一条不带目标的 mihomo 规则：
  - `type`：`DOMAIN`、`DOMAIN-SUFFIX`、`DOMAIN-KEYWORD`、`DOMAIN-REGEX`、`DOMAIN-WILDCARD`、`GEOSITE`、`GEOIP`、
    `IP-CIDR`、`IP-CIDR6`、`IP-SUFFIX`、`IP-ASN`、`SRC-GEOIP`、`SRC-IP-ASN`、`SRC-IP-CIDR`、`SRC-IP-SUFFIX`、
    `SRC-PORT`、`DST-PORT`、`IN-PORT`、`IN-TYPE`、`IN-USER`、`IN-NAME`、`PROCESS-NAME`、`PROCESS-PATH`、
    `PROCESS-NAME-REGEX`、`PROCESS-PATH-REGEX`、`PROCESS-NAME-WILDCARD`、`PROCESS-PATH-WILDCARD`、`NETWORK`、
    `UID`、`DSCP`、`AND`、`OR`、`NOT`，大小写不限。`MATCH` 只由兜底生成；`RULE-SET`、`SUB-RULE` 需要规则之外的
    配置（`rule-providers`、`sub-rules`），方案没有地方保存它们，所以不接受，转换时也不带入（8.8 节）；
  - `value`：不能为空或换行；除 `AND`、`OR`、`NOT` 和三种 `-REGEX` 外不能有逗号（mihomo 按逗号切分规则）；
  - `no_resolve`：只对 `GEOIP`、`IP-CIDR`、`IP-CIDR6`、`IP-SUFFIX`、`IP-ASN`。
- `target`：策略组 id、`region:代码`、`DIRECT`、`REJECT` 或 `REJECT-DROP`，还可以是 `egress:warp`
  （exits.md）和 `mesh:<订阅 id>/<原名>`（mesh.md），`egress:tor`、`egress:vpngate` 随 M10、M12 加入。兜底目标
  同样可以写这两种；策略组的 `others` 不能写。未知的 id 或地区代码是
  `invalid_config`；地区当前没有节点、自建组没有成员时改走节点选择并警告（8.1 节）。

**链式出口**（`egress`）

```json
"egress": {"warp": {"via": "region:JP"}}
```

- `warp.via`：WARP 出口经由的组，策略组 id（内置组、`region:代码` 或自建组），不填是 `proxy`。`DIRECT` 等内置出站、
  `region:*`、不存在的组是 `invalid_config`。经由组没有成员（包括没有节点的地区）时改走节点选择，警告 `via_empty`。
- 账户不在方案里，随 `Composition.egress` 传，属于本机（exits.md 3.2 节）。
- `tor`、`vpngate` 现在写了也被忽略，随 M10、M12 加入。

**信息节点表达式**不在方案里，随 `Composition.info_filter` 传，属于节点池设置。内核按给出的表达式原样匹配
（regexp2，区分大小写），空串表示不排除。所以 5.2 节的默认值带 `(?i)`，否则碰不到常见的 "Expire"。

### 8.6 基础段

写在 `src/core/internal/compose/base.yaml`，嵌入内核，随版本更新，不在界面上编辑；需要调整的用户用全局覆写。

- **通用**：`mode: rule`、`log-level: info`、`mixed-port: 7890`（`RunOptions.mixed_port` 非 0 时替换）、
  `unified-delay`、`tcp-concurrent`，`profile` 保存节点选择和 fake-ip 映射。
- **GEO 数据**：`geodata-mode: true`、`geodata-loader: memconservative`（按需读文件，内存占用小）、
  `geo-auto-update: true`、`geo-update-interval: 24`；`geox-url` 是 meta-rules-dat 的 `latest` 发布（与 mihomo
  的默认值相同）。
- **嗅探**：开启；HTTP（80、8080–8880，覆盖目标地址）、TLS 和 QUIC（443、8443）；跳过 `Mijia Cloud` 和
  `+.push.apple.com`；`parse-pure-ip`、`force-dns-mapping`。
- **DNS**：
  - `enhanced-mode: fake-ip`，地址段 `198.18.0.1/16`；`fake-ip-filter` 排除 `geosite:private`、局域网和本机
    后缀、Windows 联网检测、NTP 和 STUN 的域名；
  - 国内域名（`geosite:cn,private`）走国内 DoH：`dns.alidns.com`、`doh.pub`（`nameserver-policy`）；
  - 其余走 `dns.cloudflare.com`、`dns.google`，并开启 `respect-rules`，让这些 DNS 连接按规则走（通常经代理）；
  - 代理服务器的域名用 `proxy-server-nameserver` 单独解析（国内 DoH），不受规则影响；
  - DoH 服务器自己的域名由 `default-nameserver`（223.5.5.5、119.29.29.29）解析。
  - 不设 `dns.listen`：内核不开 DNS 端口；TUN 的 `dns-hijack` 直接交给内核的解析器，不需要端口
    （architecture.md §3.1）。
- 平台补丁和安全项在基础段之后应用，所以基础段里不写 `tun`、`allow-lan`、控制器等字段。

### 8.7 地区表

写在 `src/core/internal/compose/regions.go`：每行是地区代码（ISO 3166-1）、旗帜、中英文名称和正则（regexp2）。

- 顺序：HK、TW、MO、JP、KR、SG、US、CA、GB、FR、DE、NL、RU、TR、ID、IN、TH、VN、MY、PH、AU、AR、BR、AE、CN，
  最后是 `ZZ`（其他地区，CLDR 的"未知地区"）。按顺序找第一行匹配的，所以一个节点只属于一个地区，名称里提到
  两个地方时由顺序决定（"香港 IPLC 日本"归香港，"🇨🇳 台湾"归台湾）。
- 每行匹配旗帜、中文写法和城市（简繁）、不区分大小写的英文名称和城市，以及大写的代码。代码前后不能紧挨字母，
  后面可以接数字（"HK01"、"US-02" 都算，"RUSSIA"、"plus" 不算）。
- 例外：英国不认 `GB`（更常见的是流量单位，如"剩余 12 GB"），只认 `UK`、`GBR`、中文和旗帜；`CN` 后面不能接
  数字（"CN2" 是线路名），而且中国放在最后，"中国香港"之类先被前面的地区认走。
- 界面只拿地区代码，名称自己本地化；生成的地区组名称用表里的中文或英文（8.5 节 `locale`）。

### 8.8 转换与导出（M8b）

实现在 `src/core/internal/compose` 的 `convert.go`、`export.go`。

**转换**（`ConvertToPlan`，4.7 节）：
- 策略组：名为"节点选择""Proxy"的并入 `proxy`，名为"自动选择""Auto"的并入 `auto`：引用它的地方改指内置组，
  内置组保持自己的成员。其余转成自建组，类型不认识时为手动选择，测速地址、间隔、容差、超时、`lazy`、负载均衡
  策略和 `hidden` 照搬。名称与内置组、任何地区组（按方案的 `locale`）或别的组冲突时加" 2"" 3"；逗号、换行换成
  空格。`GLOBAL` 等 mihomo 的内置名称不算策略组。
- 组的成员：`proxies` 里的直连、拒绝和其他组进 `others`（组不列自己）；`include-all`、`include-all-proxies`、
  `include-all-providers` 或 `use`（订阅自己的 provider 不进节点池，所以按整个节点池算）没有 `filter` 时是
  `all`，有时每个 `filter`（反引号分隔）正好是地区表里某个地区的正则就记成这个地区，其余合成一个名称正则；
  `exclude-filter` 记成排除。`proxies` 里列出的节点：正好是全部节点（信息节点除外）时是 `all`；正好是若干地区的
  全部节点时记成这些地区；否则带来源订阅 id 时记成手动挑选，导入时（没有来源）记成只匹配这些名称的正则。
- 规则：`GEOSITE`、`GEOIP` 转成分类条目（分类名转小写，`GEOIP` 没写 `no-resolve` 时保持解析）；`DOMAIN`、
  `DOMAIN-SUFFIX`、`DOMAIN-KEYWORD` 转成域名条目，`IP-CIDR`、`IP-CIDR6` 转成 IP 段条目（规范成网络地址）；
  相邻、目标相同（IP 段还要 `no-resolve` 相同）的域名或 IP 段规则合成一条，匹配结果不变。其余能作为匹配项的
  规则各保留为一条原始规则条目。`MATCH` 成为兜底。
- 不带入方案、在摘要里逐条列出的规则：`RULE-SET`，以及含 `RULE-SET` 的逻辑规则（`rule_set`）；`SUB-RULE` 及含
  它的逻辑规则（`sub_rule`）；目标既不是组也不是直连、拒绝的（`target`）；`MATCH` 之后的（`after_match`）；
  mihomo 会拒绝的（`invalid`：不认识的类型或参数、写不对的正则或 IP 段、内核 GEO 数据里没有的分类）。
  **`RULE-SET`、`SUB-RULE` 的决定（M8b）**：方案只存规则条目，没有地方保存 `rule-providers` 和 `sub-rules`
  段，所以转换时跳过它们，并在摘要里写出条数；需要它们的用户在全局覆写里写 `rule-providers` 和
  `prepend-rules`（覆写在拼装之后应用，5.6 节）。
- 条目和组的 id 由位置和内容算出（`g-`、`r-` 加 12 位十六进制），同一份输入每次得到同一个方案。转换结果会按
  8.5 节再解析一遍，保证内核读得回来。

**链式出口与组网出站**：分享导出的规则写"WARP 出口"（或"WARP exit"）和组网出站的名称，不论本机有没有
WARP 账户；出站本身不导出，导入方的配置要自己定义。转换时，目标是这两个出口名称的规则转成 `egress:warp`；带来源
订阅 id 时，目标是这份订阅里组网出站的规则转成 `mesh:` 目标，否则跳过（`target`）。

**导出**（`ExportPlan` 的 `SHARE`）：写出与拼装结果相同的组和规则，但成员写成在别人的配置里也能算的条件：
地区和名称包含写成 `include-all` 加 `filter`（每个条件一段，反引号分隔，地区用地区表的正则），全部节点写成
`include-all`，排除写成 `exclude-filter`；其他成员、手动挑选的节点、来源订阅的节点和"其他地区"的节点按订阅里的
原名列在 `proxies`。不含节点本身和 provider。mihomo 的 `exclude-filter` 也作用于 `proxies` 里的成员，一个名称
同时提到两个地区的节点在别人的配置里会进两个地区组，这两点与本机的拼装不同。导出的片段再导入时，地区条件
还原为地区。

## 9. 数据与存储

- 存进 SQLite（[storage.md](storage.md)），并进入备份快照。表结构见 `models/database.py`：
  - `routing_state`：分流方式、"订阅自带"时用的订阅、"我的方案"时用的方案、节点池设置；
  - `plans`：`id`、名称、兜底目标、`egress`（链式出口的设置，exits.md 7.1 节）、位置、时间戳、软删除；
  - `plan_groups`：主键 `(plan_id, id)`，有名称、种类（内置 / 地区 / 自建）、类型、条件（JSON）、高级参数（JSON）、
    是否隐藏、位置，可软删除；
  - `plan_rules`：`id`、方案、位置、是否启用、种类（服务 / 分类 / 域名 / IP 段 / 原始）、内容（JSON）、目标，可软删除；
  - `profiles` 有 `in_pool`（是否加入节点池）。
- 目标存策略组 `id`、`DIRECT`、`REJECT`、`egress:warp` 或 `mesh:<订阅 id>/<原名>`；地区组的 `id` 由地区代码派生，
  节点池变化后保持不变。

## 11. 取舍

| 没有采用 | 采用 | 原因 |
| --- | --- | --- |
| 每份订阅有用途（完整配置 / 节点源），导入时选择 | 一个全局的分流方式；订阅只有"是否加入节点池" | 导入时的用途问题新手答不上来；"当前使用"分散在两个页面 |
| 方案列表占分流页左栏 | 方案是标题栏下方的下拉框 | 多数人只有一套方案 |
| 规则与内核规则一一对应 | 一个规则条目表示一个意图，可以展开成多条 | 列表短，读起来像"谁走哪里"；需要核对时看生成的配置 |
| 策略组编辑器默认展开全部条件 | 默认只有地区，其余收进"更多条件" | 新手只需要地区 |
| 编辑正在使用的方案后点"应用" | 每次确认的改动立即生效，连续操作合并 | 忘记点"应用"比多一次重载代价更大 |
| 手动挑选的节点也受排除影响 | 手动挑选和其他成员不受排除影响 | 手动挑选是明确的意图 |
